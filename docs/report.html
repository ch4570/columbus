RepoAtlas 탐색과 토큰 효율 관측

2026-09-07 · RepoAtlas 0.4.0 · 로컬 조회 측정 + 실제 Codex 탐색 6회

RepoAtlas는 에이전트가 읽는 코드의 범위와 반복 전송을 줄입니다. 이번 관측에서 같은 28개 지도 항목의 텍스트 출력은 JSON보다 46.8% 작았습니다. 하지만 실제 에이전트 비교에서는 누적 입력 토큰 절감을 입증하지 못했습니다. 양쪽 답변이 인용 검사를 모두 통과한 사례에서는 입력 토큰이 오히려 34.0% 늘었습니다.

작은 출력, 적은 도구 호출, 정확한 답변, 모델 사용량을 따로 측정해야 합니다. 아래 수치는 유리한 결과와 불리한 결과를 모두 포함합니다. 영문 재현 안내에서 직접 실행할 수 있습니다.

추정 토큰은 ceil(UTF-8 응답 바이트 / 3)입니다. 바이트와 토큰 예산을 함께 주면 더 작은 상한을 사용합니다. CLI의 map 기본 상한은 6,000바이트, context는 12,000바이트입니다. 전송 계층과 호스트 프롬프트 비용은 별도입니다.

1. 같은 예제에서 CLI 응답 측정

번들에 포함한 examples/polyglot-demo를 임시 디렉터리에 복사해 색인했습니다. 11개 파일, 28개 심볼, 25개 관계이며, 소스·엔진 파일 해시를 delivery.json에 보관합니다. 모델을 호출하지 않는 측정입니다.

두 형식이 충분히 들어가는 30,000바이트 상한에서 동일한 순서의 28개 심볼 ID를 반환했는지 검사했습니다.

응답 바이트가 46.8% 줄었습니다. 텍스트는 위치·선언·분석 수준을 남기고 반복 필드 등을 줄입니다. JSON 전체 메타데이터와 동일한 정보량이라고 주장하지는 않습니다. 상한을 6,000바이트로 낮추면 JSON은 24개 항목을 담고 4개를 생략한 반면, 텍스트는 28개를 모두 담았습니다.

Receipt 없이 같은 조회를 반복하면 앞의 소스를 다시 받습니다. Receipt를 사용한 두 번째 조회는 아직 전달하지 않은 188바이트를 이어 읽고, 세 번째는 소스 없이 상태만 반환했습니다. 세 번의 전체 응답 합계는 9,633바이트에서 4,483바이트로 53.5% 감소했습니다. 서로 같은 소스 집합을 세 번 받은 비교는 아니며, receipt가 추가로 읽지 않은 범위를 전달했다는 점을 함께 봐야 합니다.

서로 겹치는 부모·자식 심볼도 전달한 문자 범위로 중복을 판단합니다. 원본 바이트 해시와 디코딩·줄바꿈 정규화 후 해시가 모두 맞아야 이전 범위를 재사용합니다. 파일 내용이나 디코딩 설정이 바뀌면 새로운 소스를 숨기지 않습니다. 긴 함수나 긴 한글 줄도 나머지를 이어 읽도록 회귀 테스트했습니다.

Receipt는 이 작업에서 실제로 이전 출력을 받은 에이전트만 재사용합니다. 컨텍스트가 사라진 새 세션이나 다른 에이전트에는 새 receipt를 써야 합니다. 변경 없는 후속 sync에서는 parsed_files=0, hashed_files=0, hashed_bytes=0이었습니다.

재현 명령은 다음과 같습니다. 임시 색인·receipt·telemetry는 실행 후 정리됩니다.

python scripts/observe_delivery.py

2. 실제 에이전트의 탐색 비교

조건

코드 위치를 찾아 근거를 설명하는 질문 세 개를 먼저 고정했습니다. 질문별로 일반 탐색과 RepoAtlas 사용 탐색을 각각 한 번 실행했습니다. 일반 탐색에도 효율적인 rg와 필요한 줄만 읽기를 허용했습니다. 전체 파일 덤프를 강제한 비교가 아닙니다.

두 조건 모두 같은 전역 스킬 목록이 보였습니다. 스킬 설명 축약 경고가 있었으며 이 시작 비용은 빼지 않았습니다. RepoAtlas 조건의 안내 프롬프트는 도구 사용법 때문에 더 깁니다. 모델 이름은 요청한 alias이며 공급자의 내부 모델 버전을 증명하지 않습니다.

답변은 지정한 파일, 40줄 이하의 유효한 소스 범위, 실제 원문 인용, 설명을 반환해야 합니다. 인용의 들여쓰기는 무시하지만 임의 생략 부호는 통과시키지 않았습니다. 모든 답변에 같은 v2 검사기를 적용하고 초기 판정도 보존했습니다. 설명의 메커니즘은 소스와 대조해 별도로 검토했습니다.

캐시된 입력은 전체 입력의 부분집합입니다. input + cached_input으로 더하지 않습니다. 출력 사용량에 reasoning 수치를 다시 더하지도 않습니다. 명령 수는 완료한 shell command 항목 수이며 모델 왕복 횟수와 같지 않습니다. 명령 출력 바이트는 CLI에 기록된 문자열의 길이로, 모델에 전달된 전체 도구 메시지의 토큰 수와 다릅니다. 가격이나 청구 금액은 계산하지 않았습니다.

양쪽이 인용 검사를 통과한 export 사례에서는 캐시되지 않은 입력은 1.4% 줄었지만, 전체 입력과 출력은 늘었습니다. 이번 비교로 모델 토큰 절감을 입증할 수 없습니다. 단일 저장소의 세 가지 읽기 질문이며 장기 구현 작업, 대형 저장소, 다른 모델에 대한 성능 결론도 내리지 않습니다.

실제로 어떤 탐색을 했는가

Export 사례의 RepoAtlas 에이전트는 자연어 검색 세 번 후 CLI 앞부분, 넓은 rg, 정확한 줄 범위를 읽었습니다. 검색 출력은 각각 약 1.2KB였지만 뒤의 넓은 검색은 47KB였습니다. 앞의 검색이 뒤의 읽기를 충분히 대체하지 못했습니다. 입력 토큰에는 단계마다 다시 처리한 대화 문맥도 포함되므로 작은 검색 응답만 합쳐 비용을 판단할 수 없습니다.

설치 충돌 사례에서는 검색 → 해당 파일에서 rg → 필요한 세 범위를 읽었습니다. 명령 출력이 23,514바이트에서 11,993바이트로 49.0% 감소했지만 누적 입력은 늘었습니다. 실행마다 달라지는 캐시와 모델의 진행 방식도 포함된 결과입니다. 이 파일 위치 탐색에서는 receipt 사용까지 진행하지 않았으므로 CLI의 중복 제거 수치를 실제 에이전트 사용량 감소로 연결하지 않습니다.

제외한 초기 실험도 보존

초기에는 상위 Git 저장소에서 무시하는 .omx 아래에 소스를 풀어 색인이 0파일이 되는 문제가 있었습니다. RepoAtlas 실행 두 번이 빈 검색 후 일반 읽기로 돌아갔습니다. 해당 초기 5회 전체를 성능 비교에서 제외하고, 원인과 관측값을 excluded-preflight.json에 남겼습니다.

실험 준비 시 독립 Git 루트를 만들고, 파일·심볼·색인 바이트가 0보다 큰지 확인하는 검사를 추가한 뒤 세 쌍을 새로 실행했습니다. 제품도 사용자가 명시한 루트가 상위 Git의 ignore에 들어 있는 경우 파일 시스템 탐색으로 돌아가도록 고쳤고, 기존 ignore 동작과 함께 회귀 테스트했습니다.

관측을 반영한 사용법

  1. 이름이나 파일을 알면 직접 좁힙니다. 알려진 리터럴에는 특정 경로의 rg나 직접 읽기가 더 간단할 수 있습니다.
  2. 구조를 모를 때 작은 지도를 봅니다. 개념의 위치는 짧은 검색, 관계가 필요할 때는 정확한 ID와 neighbors를 사용합니다.
  3. 빈 검색을 표현만 바꿔 반복하지 않습니다. 색인 coverage를 한 번 확인하고 파일·디렉터리·짧은 키워드로 전환합니다.
  4. 필요한 소스에만 예산과 receipt를 씁니다. 독립 조회를 묶고, 근거가 충분하면 탐색을 마칩니다. 단계 수를 줄이는 것도 중요합니다.
  5. 응답과 런타임 사용량을 함께 봅니다. 모델·질문·정확성·캐시를 고정하거나 기록한 다음 개선 여부를 판단합니다.

이 원칙을 설치되는 스킬과 에이전트 안내에 반영했습니다. 관측 후에는 긴 함수·클래스의 앞부분만 전달하던 한계도 고쳐, 선언 범위 안의 검색 일치점을 먼저 보여주도록 했습니다. 정확한 이름 검색은 헤더를 유지하고, receipt로 앞뒤 남은 코드를 이어 읽습니다. 이 후속 수정은 기능 테스트로 검증했으며 위 모델 비교 수치에는 소급 적용하지 않았습니다. 관측 당시 엔진 ZIP을 따로 보존합니다.

repoatlas context checkout --format text --budget-tokens 2000 \
  --receipt .repoatlas/checkout-receipt.json \
  --telemetry .repoatlas/exploration.jsonl
repoatlas telemetry .repoatlas/exploration.jsonl --format text

Telemetry에는 원문·질문·소스 경로를 쓰지 않습니다. Receipt에는 상대 경로·해시·전달 범위를 기록합니다. 서로 다른 파일에 저장하고, 동시 에이전트는 별도 파일을 사용합니다. 자세한 계약은 에이전트 연동에 있습니다.

근거와 재현

  • 실제 탐색 6회 기록: 모델 설정, 프롬프트, 명령과 출력 크기, 답변, 판정, 사용량, 파일 해시.
  • CLI 조회 기록: 같은 지도 항목과 receipt 비교, 현재 소스·엔진 해시.
  • 관측 하네스: 입력·출력 스키마, 원본 fixture, 관측 엔진, 실행 절차.
  • 제품 검증 기록: 자동 테스트, 설치 패키지, 플랫폼 범위와 남은 한계.

원본 이벤트 JSONL은 로컬에 보존하고 공개 기록에는 SHA-256을 남겼습니다. 공개본은 실행 경로를 치환하고 답변·명령 메타데이터만 포함하며 내부 추론 로그는 포함하지 않습니다. 공개본만으로 공급자 청구를 독립 인증할 수는 없습니다.
