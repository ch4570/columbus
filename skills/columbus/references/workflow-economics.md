# 명시적인 워크플로우와 완료 비용

Columbus는 사용자가 원하는 목표·범위·근거·종료 조건을 짧게 명시하고, 현재 부족한 근거에 맞춰 도구를 선택한다. 실행 규칙의 기준은 [SKILL.md의 작업 계약](../SKILL.md#task-contract)이다. 이 문서는 워크플로우를 설계하거나 경제성을 평가할 때만 읽는다.

## 상황별 선택과 종료

| 현재 상태 | 선택 | 종료 또는 전환 |
| --- | --- | --- |
| 파일과 식별자를 안다 | 해당 경로의 검색이나 소스 범위를 바로 읽는다 | 요청한 근거가 충분하면 탐색 종료 |
| 저장소 구조를 모른다 | 작은 map으로 관련 경로를 찾는다 | 후보를 찾으면 필요한 선언·소스로 좁힌다 |
| 검색이 비거나 무관하다 | coverage를 한 번 확인한다 | 경로·짧은 식별자·직접 읽기로 바꾼다; 표현만 바꿔 반복하지 않는다 |
| receipt 조회가 소진됐다 | `has_more`와 omission, 미해결 질문을 확인한다 | 질문이 해결됐으면 종료; 부족하면 다른 진입점으로 전환한다 |
| compaction 또는 담당 에이전트 변경 | 새 receipt/session으로 필요한 근거를 다시 읽는다 | 이전 전달 기록을 현재 기억으로 간주하지 않는다 |

작업 계약은 이미 제공된 정보를 반복 질문하거나 별도 계획 문서를 만드는 절차가 아니다. 다음처럼 작업에 필요한 조건만 명시한다.

```text
목표: 결제 취소 경로와 재시도 조건을 소스 위치와 함께 설명한다.
범위: 결제 모듈. 알고 있는 식별자에서 시작한다.
완료 근거: 취소 진입점, 상태 변경, 재시도 조건의 원문 위치.
전환: 검색이 무관하면 coverage 확인 후 경로를 좁힌다.
종료: 요청한 세 근거와 남은 분석 한계를 설명할 수 있을 때.
```

예산 소진은 완료가 아니다. 현재 응답 상한, 누적 로컬 전송량, 모델의 전체 사용량은 서로 다른 지표다. 한도가 있으면 넘기기 전에 필요한 범위를 줄이거나 불완전 상태를 명시한다. 사용자가 정한 목적·권한·필수 검증을 비용 때문에 생략하지 않는다.

## 경제적으로 사용하는 방법

- 상시 진입점에는 작업 계약·라우팅·핵심 불변 조건을 둔다. hooks/export/MCP 같은 선택적 절차는 요청이 있을 때 해당 reference에서 읽는다.
- 아는 파일은 다시 지도부터 찾지 않는다. 독립 조회는 묶고, 긴 출력은 근거에 필요한 범위로 제한한다. 재시도에는 새로 얻을 근거와 전환 조건이 있어야 한다.
- receipt는 같은 에이전트가 이전 소스를 보유하는 동안만 재사용한다. 미전달 코드 때문에 줄어든 바이트를 절약이라고 계산하지 않는다.
- 검증·집계는 가능한 기존 테스트와 스크립트로 처리한다. 위임은 독립적인 조사·검증의 이득이 있을 때만 하고 목표·관련 경로·완료 조건을 전달한다. 부모와 자식의 전체 비용을 합산한다.
- 모델은 호스트에서 실제 사용 가능한 후보와 작업 난도·검증 결과에 따라 선택한다. 모델 ID나 가격을 이 스킬에 고정하지 않는다.
- 반복되는 고정 지침은 캐시될 수 있지만, 지침 충돌로 생기는 불필요한 판단과 재작업은 따로 관측해야 한다. 긴 고정 입력의 토큰 수만으로 청구 비용을 판단하지 않는다.

## unharness 논의의 범위

원문 확인일은 2026-09-09다. unharness가 하나의 합의된 방법론이라고 가정하지 않는다.

[John Berryman의 글(2026-04-24)](https://arcturus-labs.com/blog/2026/04/24/unharnessed-agents-power-the-future-of-ai-products/)은 에이전트를 IDE·터미널·코딩 보조라는 틀 밖으로 확장하고 조합 가능한 구성 요소로 다루자는 주장이다. 같은 글이 skills를 지지한다. 이 용례는 사용자 workflow를 명시하는 것과 충돌하지 않는다.

[Anthropic의 글(2026-07-24)](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)은 특정 모델에서 시스템 프롬프트를 80% 이상 줄여도 자체 코딩 평가 손실이 측정되지 않았다고 보고하고, 팀 고유 지침을 필요할 때 읽는 skills로 옮기는 방법을 설명한다. 80%는 시스템 프롬프트 감소량이지 전체 토큰·비용 절감률이 아니며, 다른 모델과 저장소에 그대로 일반화할 수 없다.

이 프로젝트에서는 의도와 검증 기준을 유지하면서 중복 지침과 불필요한 필수 단계를 줄인다. 명시적 workflow가 경제적인지는 같은 품질에서의 실제 완료 비용으로 판단한다.

## 검증 기준

도구 유무와 추가 workflow 정책 유무를 분리해 같은 작업을 비교한다. 목적·권한·완료 기준은 모든 조건에 제공한다. 성공 여부와 근거 완전성, 실패·재시도, 모델 입력·캐시·출력, 도구 호출, delegate 비용, 경과 시간을 함께 기록한다. 캐시 입력이나 출력에 이미 포함된 추론량을 중복 합산하지 않는다.

가격이 확인됐을 때만 서로 겹치지 않는 과금 수량과 단가를 곱한다. 실패 비용도 포함한 총비용을 완료한 작업 수로 나누며, 성공 0건 또는 사용량 미확인은 비교 불가로 둔다. 바이트/3 추정치를 청구 토큰으로 바꾸지 않는다. [공식 캐시 설명](https://developers.openai.com/api/docs/guides/prompt-caching)도 일반 입력·캐시 읽기·캐시 쓰기를 구분한다.

현재 구현·후속 작업은 [세션 누적 예산 #36](https://github.com/ch4570/columbus/issues/36), [품질을 고정한 비용 비교 #37](https://github.com/ch4570/columbus/issues/37)에서 추적한다. 실측 전에는 일반적인 절감률을 주장하지 않는다.

2026-09-09의 후속 네 조건 관측은 24회 중 22회가 근거 품질을 통과했고 2회는 Unicode 인용에 실패했다. 도구 제공 조건에서도 Columbus가 선택되지 않아 실제 도구·세션 예산의 경제적 효과나 비용 회수는 확인하지 못했다. 추가 정책의 입력 변화도 비교 범위에 따라 방향이 달랐다. 따라서 조건부 선택과 짧은 작업 계약을 유지하며, 도구 사용을 강제하거나 일반적인 절감률을 광고하지 않는다. 자세한 수치와 실패를 포함한 원자료는 프로젝트의 `docs/workflow-cost.md`와 `evals/exploration/results/2026-09-09-workflow/controlled.json`에 보존한다.
