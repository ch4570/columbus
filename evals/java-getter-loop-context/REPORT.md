# Getter return-type namespace controls

Before enabling getter-based loop bindings, three cross-package Java cases fix the required type context. a.Source.items returns Collection<Item> in package a; package b separately declares an unrelated Item. In b.C, both an explicitly declared a.Item loop variable and var compile to a/Item.hit. Declaring the variable as the consumer package's Item fails compilation because the elements are a.Item.

Both current parser environments leave all three loop-body calls unresolved. The two valid missing calls are coverage gaps, not successful resolution. javac diagnostics, javap owner references, source files/hashes, analyzer hash and tool versions are retained. Any emitted target must match the manually declared static owner. No code is executed and no runtime-dispatch claim is made.

A getter implementation must carry the return declaration's file/scope type identity into the consumer. Copying the bare return argument Item into the caller scope could choose b.Item, especially for var. This adds a concrete namespace guard to the previously fixed same-file collection cases; it does not redefine their success criteria or claim getter support already exists. The full loop-resolution and actual-token objectives remain open.

Preparatory reference linkage: enhanced-for method-invocation expressions now retain the exact root reference index in their loop's iterable fact. The original reference remains in the enclosing scope. A regression test checks nested argument calls and two loops on one source line, so neither a nested call nor a line-based match can substitute for the root call. The resolver still rejects this new call fact pending declaration-context return-type handling. Both parser environments pass 254 engine tests; 53 distribution tests pass. The repeated compiler control in reference-link-check.json still reports zero resolved body calls across the three cases, including the two valid coverage gaps. This change provides no measured token savings.

Getter resolution now follows the saved iterable reference through the normal resolver and reads its concrete array or standard-collection return type in the declaration's file and scope. Inferred var bindings carry that scope through member lookup, nested loops and argument identity checks. Explicit getter-loop variables also receive argument conversion checks. A new test caught a wrong-package argument being accepted by the pre-existing unknown-expression path; inferred-loop argument conversions now reject incompatible or unsupported identities. Type parameters, return-signature names polluted by body-local declarations and wildcard elements remain conservative gaps.

The unchanged three cross-package compiler fixtures now resolve both valid calls to a.Item.hit and leave the invalid b.Item declaration unresolved, in both ordinary and candidate parser environments. `--require-getters` makes the two positive targets blocking CI requirements. The previous iterable-scope verifier's historical unresolved expectations were updated to exact compiler-confirmed targets for valid loop bodies and nested iterable calls; wrong-argument rejection remains mandatory. Original source fixtures and historical reports are retained.

Validation: 255 engine tests pass in each parser environment, 53 root tests pass, 103 existing compiler controls pass, and clean wheel/ZIP installation checks pass. The 14 array controls resolve 7/10 expected valid calls (previously 6/10); ten collection controls resolve 4/7 (previously 2/7). These denominators count valid calls, and remaining misses are gaps. Raw compiler results are adjacent JSON files.

Spring comparison uses the same 1,166 file hashes: six added edges, zero removed, 33,014 total edges. The added DefaultResourceLoader.getResource -> ProtocolResolver.resolve declaration matches the loop's Collection<ProtocolResolver> getter and interface declaration. The other additions are matchInterface(String), three ReflectionUtils FieldCallback/FieldFilter calls, and AnnotationTypeMapping.getAnnotationType; the loop declarations, getter signatures and call sites were inspected in source. This is a targeted static declaration review, not an unbiased precision sample or a full Spring compiler/type-applicability proof. In particular, the existing unknown-expression handling of `this` is not newly proven by the ProtocolResolver edge. No model trial was run for this change; quality-preserving actual total-token savings remain unproven.

Incremental invalidation regression: `test_java_getter_loop_relinks_unchanged_consumers` keeps the consumer and both Item declarations unchanged while changing the getter's import from a.Item to b.Item, deleting the getter file, and restoring the original import. The unchanged consumer's hit target switches from a.Item to b.Item, becomes unresolved on deletion, and returns to a.Item on restoration. Every stage compares all decoded per-file facts and the full graph with a fresh index. Import changes parse only one file; deletion parses none. The final facts equal the initial snapshot. Both ordinary and candidate environments pass all 256 engine tests, including this regression. This proves the tested cross-file invalidation path, not a general incremental-performance claim.
