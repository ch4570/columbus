# Spring source audit after type-receiver resolution

The real-corpus audit found both useful restored navigation and unresolved correctness work. On identical fresh syntax facts, the `f6a7530` resolver produced 9,339 call edges and the `9a249be` resolver produced 9,349: 42 additions and 32 removals. This net increase is not a precision or recall measurement.

The source is Spring `4c8c6409a27a62ab163d3b6196ad862b7c835440`, spring-core, with 1,166 indexed files and 7,120,331 source bytes. The candidate Java grammar parsed all 1,091 Java files without recovery. The complete graph still has two other diagnostics. Tracked source was clean and all indexed sources were tracked; hashes were checked after the observation. An AST comparison of the engine module confirmed that syntax extraction was unchanged between the two resolvers. Both operate on the same freshly parsed records. The approximately 6.06-second observation ran on the existing local filesystem/cache state and is not a latency benchmark.

All 42 added call spellings were reviewed against their corresponding static declarations in the original source (32 additions in production code). Examples include AccessControl.Visibility, MethodParameter.KotlinDelegate, Nullness.KotlinDelegate, PlaceholderParser.Part, and SerializationUtils helpers. `added-source-review.txt` retains the declaration/call excerpts and `source-review.json` states the scope of each review. This confirms source-level declaration matches; it does not prove full argument applicability or runtime behavior across Spring.

All 32 removed edges are supported generic source calls, rather than demonstrated false targets: thirteen `asArray(T...)`, ten `ArgumentResolver.of(Class<T>, T)`, five `match(InstanceFilter<T>, T)` and four `doNotMatch` calls. Source review checked the signatures, relevant imports and String/String-compatible arguments. They are lost coverage because the resolver cannot prove the generic conversion. Reduced javac fixtures confirm the relevant valid-call patterns; Spring itself was not compiled or executed.

The generic audit also reproduced a remaining false-edge mechanism. `Factory.hit(String.class, Integer.valueOf(1))` with signature `<T> void hit(Class<T>, T)` is rejected by javac, but currently resolved by Columbus. A similar conflict between `Filter<String>` and an Integer expression is also incorrectly resolved. The parser records nonliteral expressions with unknown argument types, and the literal-only guard skips them. Conversely, valid String literal calls can be rejected as unsupported generic conversions.

Eight reduced fixtures were observed with javac 17.0.20.1 under both pinned and candidate Java parsers. Both runs agree: two compiler-invalid calls are resolved, four valid calls are omitted, one valid expression call resolves, and one invalid literal call stays unresolved. `generic-constraints.json` and `generic-constraints-candidate.json` deliberately record a failed observation gate. These failures are not hidden behind the prior twenty-four passing fixtures, nor represented as a passing new regression suite. Only generated literal fixtures were compiled with `-proc:none`.

The next implementation must retain sufficient argument type facts to check correlated type variables (such as `Class<T>, T` and `Filter<T>, T`) and unbounded generic varargs. Unknown expression types must not bypass a needed compatibility check. Positive generic examples must remain in the acceptance corpus alongside the two false edges; simply reporting more unresolved references is not the final objective. Full expression typing and generic inference are still incomplete, so issue #8 cannot be closed.

The current complete archive was also verified: 4,790,642 bytes, 20,811 nodes, 31,583 edges and 68,007 references, with no output truncation. A source-free lookup from an empty consumer directory returned Visibility.forClass in 800 bytes under a 2,048-byte budget and created no SQLite database or files. `archive-check.json` retains the archive hash and response. The active SQLite cache was 108,265,472 bytes; the small portable artifact does not mean the SQLite amplification problem vanished. This is a size/query observation, not actual-model token savings. The archive and frozen resolver copies are retained at `.omx/observations/spring-type-receiver`; the full raw observation, including the SQLite database, remains at `/tmp/columbus-spring-type-receiver-review`. The duplicate database was removed from the repository observation folder.

The preceding type-receiver commit completed six ordinary distribution jobs and thirteen candidate/aggregate jobs. Those checks cover their declared fixtures, not the newly discovered generic failures. No engine behavior or model prompt was changed during this audit, and no model trial was rerun. The overall goal remains open.
