# Local methods with a complete explicit base chain

The previous resolver rejected every non-constructor call whose receiver/owner had an explicit base, even when a local declaration had no competing name anywhere in the base chain. This suppressed DefaultResourceLoader.getResourceByPath(location) at line 166, one of the source-reviewed omissions in issue #4.

The resolver now allows existing local-member lookup when every explicit Java base resolves uniquely and no base or transitive ancestor declares the member name. Unknown, partial, generic, inaccessible, cyclic and non-Java bases keep the inherited-candidate gate. A name present in any base also retains the gate: this change neither chooses inherited overloads nor merges override signatures. The existing local shadowing, instance/type receiver, accessibility, argument and generic checks still run. Absence results are cached only for the current global resolver instance, so refresh reconstructs them from the new complete snapshot.

Both parser environments pass 241 engine tests and the root suite passes 53. The tests include an intentionally partial base file and receiver shadowing. The compiler gate extends the prior 84 cases to 103, including six newly resolved valid calls, competing base/interface overloads, unknown ancestry, generics, cycles, wrong argument types and invalid receivers. Javac 17 results and full references/edges are saved in pinned.json and candidate.json. A replay of the unchanged saved baseline runtime fails exactly the six new positive cases; all other expectations pass. The malformed-base test is a parser/unit guard, separate from this compiler corpus.
