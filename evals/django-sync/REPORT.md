# Django unchanged-sync diagnosis and control-character scan

The current full Django corpus still incurs substantial discovery work during unchanged fast sync. Before this change, three sequential warm syncs had a 3.4023-second median despite zero parsed files, zero cached parses loaded and zero source hash reads recorded by refresh. Inventory reports 3,907 probed files and 24,486,875 probe bytes per discovery pass. The profile observes two discovery calls; these probe reads are separate from refresh's hashed_bytes counter and must not be called zero source I/O.

The profiled Python generator for character classification ran approximately 32.49 million times, accounting for 5.44 seconds cumulative in a 12.83-second profiled sync. Profiling overhead is substantial and those timings are not ordinary latency. Replaced this per-character Python predicate with a compiled character-class search that rejects exactly code points 0–7, 11 and 14–31. UTF-8 decoding, Python encoding cookies, file reads, binary exclusions and snapshot checks are unchanged.

After the change, the median of three warm syncs was 2.7517 seconds, about 19.1% lower in these observations. Database size remained 147,763,200 bytes. Both runs use disposable copies of the same Django checkout and include a one-file comment edit and restoration; current.json and regex.json retain all observations and profile summaries. The copies omit Git metadata and therefore use filesystem discovery. OS caches were not flushed; baseline ran first; other test processes overlapped portions of the changed run. Treat the timing difference as diagnostic evidence rather than a clean causal benchmark or a Spring issue acceptance result.

The original and new classifiers returned exactly the same full Django paths and inventory. Regression tests cover the control-character policy, binary/text transitions and existing stale-source behavior. Both parser environments pass 218 engine tests, and the root suite passes 53 tests. Search identity and graph counts were checked during edits; this is explicitly narrower than full search ranking or edge parity. The change does not address repeated reads or all path-resolution overhead and does not establish model token savings. Issue #6 remains open.

## Complete probe accounting

Sync now reports refresh.discovery_probe_files and refresh.discovery_probe_bytes across both discovery passes; the bounded summary preserves these counters. Previously the displayed inventory counter represented one pass and zero hashed_bytes could obscure ongoing content inspection. Counts include binary exclusions and repeated reads, and are application probe volume rather than total or physical disk I/O. A regression verifies an unchanged source-plus-text-plus-binary fixture: zero hash bytes and parse work, but four probes with exactly twice the two asset sizes. Both engine environments pass 219 tests and the root suite passes 53 tests. This accounting change does not eliminate either pass: the final discovery is required to detect membership/classification changes during the transaction. A future cache must preserve that invariant, including excluded-file transitions and platform metadata semantics.
