# Bundled Java parser default for the ZIP bootstrap

A ZIP built with `scripts/build_bundle.py --java-wheelhouse PATH` now carries the annotated-varargs candidate wheels, their licenses, exact-version constraints and a byte inventory. Its bootstrap discovers and verifies the bundled payload when no external wheelhouse is supplied. It requires `0.23.5+columbus.1`, including when checking an existing runtime; incompatible/missing candidate wheels cannot silently select upstream 0.23.5. An explicit user wheelhouse continues to override the bundled payload.

Local macOS arm64 / Python 3.11 evidence:

- [Existing-runtime upgrade and relocation](upgrade.json): the unchanged Java fixture moves from partial to complete after installing from the bundled ZIP with **no --wheelhouse option**. Moving the extracted source before a third run preserves candidate version and skips pip. Pinned → candidate → candidate versions and true → false → false partial flags are checked.
- [Clean installation](distribution.json): wheel and standalone installations use the explicit candidate wheelhouse; the ZIP installation omits it. All three load the exact candidate and pass four annotation cases. The ZIP also passes relocated-source execution, graph/AST output, complete archive export, source-free lookup, bounded callers, receipt continuation, hooks, and local-edit preservation.
- [Negative fallback probe](fallback.json): an available compatible upstream wheel succeeds without the local-version constraint. With the same wheel directory plus a deliberately incompatible candidate platform tag, the exact bundled constraint makes pip resolution fail. The dry runs do not modify a runtime.
- 51 root tests pass, including byte-reproducible ZIP creation, complete inventory, payload tampering rejection and incorrect candidate-version rejection. The tested ZIPs and wheel are identified by [artifact hashes](artifacts.json). Upgrade and clean-install ZIP hashes differ because the verifier/workflow source was added between builds; each receipt identifies its own observation.

The candidate workflow now builds this ZIP and runs default upgrade/relocation, negative fallback and clean installation across Ubuntu/macOS/Windows × Python 3.11/3.14. Hosted results for this new change are pending. The earlier explicit-wheelhouse upgrade completed both six-job matrices at 88e20ce; see [that report](../bootstrap-upgrade/REPORT.md).

This is a usable bundled installation path, not a public release. The ordinary release workflow still builds a ZIP without embedded candidates and the ordinary Columbus wheel still has the upstream dependency pin. A release must aggregate compatible candidate wheels for its supported systems and select the bundled build path; standalone default download remains separate work. A one-platform wheelhouse produces a ZIP whose bundled Java support is limited to that wheel's tags. Remaining dependencies still come from the configured package index. Inventory hashes and matching metadata are integrity/version checks, not independent source-build attestations. The upstream revision, generated-parser provenance and platform validation remain in the grammar build workflow. Broad newly eligible edge precision and actual model-token savings are still unproven.
