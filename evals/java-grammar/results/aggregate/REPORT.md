# One shared parser ZIP across the supported matrix

The candidate workflow now assembles one ZIP from its successful Python 3.11 OS builds, then passes those identical bytes and one Columbus wheel to six fresh consumers (Ubuntu/macOS/Windows × Python 3.11/3.14). Consumers verify artifact hashes before installation and after verification; they do not rebuild or substitute parser wheels.

`aggregate.py assemble INPUT OUTPUT` requires all three OS inputs, the pinned upstream revision and patch, valid/invalid grammar checks, passing installation receipts, matching generated sources, and wheel-native binary hashes equal to the binaries actually tested. It retains every chosen wheel hash and provenance record in aggregate.json. Distinct same-platform Python 3.14 builds are deliberately not merged under colliding wheel filenames: the shared Python 3.11 abi3 builds must instead pass the Python 3.14 consumers.

`aggregate.py verify ARTIFACTS OUTPUT` checks the shared manifest and ZIP inventory, compares bundled wheel bytes with the selection, runs clean wheel/standalone/ZIP installation checks, then verifies existing-runtime upgrade and source relocation. ZIP installs omit --wheelhouse and use their embedded candidate; wheel and standalone paths still use the extracted explicit wheelhouse. Both final artifact hashes and source revision are recorded per consumer.
