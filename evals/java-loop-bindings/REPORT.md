# Loop binding expansion controls

Ten isolated Java programs establish a before-state for the remaining loop-body gap in issue #4. Manually specified static declaration owners are checked against javac success/failure and javap call-owner output for valid programs. The current analyzer has no false emitted targets in these controls, but resolves only one of seven expected valid calls: the outer field call after a loop. Six valid loop-body calls remain unresolved in both Java grammar environments. This is a coverage gap, not seven correctly resolved calls.

The controls cover an explicitly typed array loop, field shadowing and restoration after the loop, iterable evaluation before the loop variable binding, nested arrays, var inference and a generic type parameter shadowing an unrelated concrete class. Negative programs cover out-of-scope use, wrong call arguments, incompatible iterable elements and illegal local-name redeclaration. Negative-program calls remain unresolved in this gate; compilation failure does not independently identify a valid call declaration there.

A naive change that merely assigns the declared loop variable type and removes the opaque scope would need additional checks for incompatible element types and forbidden local redeclarations. Therefore the body is not enabled based only on a successful simple array example. Future implementation must preserve field restoration, generic namespace separation and nested unsupported scopes, while documenting any still-unresolved var/generic cases. These controls are declared before loop-body expansion, not after selecting a passing implementation.

Raw Java source, hashes, compiler diagnostics, bytecode and analyzer references are retained in before.json and candidate-before.json, with parser/compiler/Python versions and analyzer hash. The probe does not execute repository code or assert runtime-dispatch targets. The ten-case corpus is diagnostic, not whole-Spring precision or a token-efficiency experiment. No runtime behavior changed in this step; the iterable-expression fix remains intact and the full loop-binding work remains open.

The first expansion resolves explicit loop variables over array parameters or validated enclosing loop arrays when element and variable type identities match. Of the same seven valid calls, four now resolve (before: one); no emitted target violates the ten-case oracle. Wrong iterable elements, conflicting enclosing local names and out-of-scope uses remain rejected. Field shadowing is restored after the loop; nested explicit array bindings work. var, generic elements, getter/collection expressions and local/field arrays remain unsupported pending inference, declaration-order and access checks. The current Spring protocolResolver loop is collection-based and is not claimed fixed by this array step.

Both Java grammar environments pass the ten compiler cases with --require-array-bindings, which now makes regression of the three supported positive scenarios fail. The previous 103-case compiler gate passes. Full engine tests pass 252 in each environment and root checks pass 53; final wheel/ZIP verification passes. Unit controls also reject a later-declared local array and an instance-field array used from a static method. CI runs the strengthened compiler probe on JVM/loop-probe changes.

A fresh index of the same 1,166-file Spring corpus adds thirteen edges and removes none relative to the iterable-expression version. Source hashes match. The delta is retained in spring-array-diff.json; these thirteen additions are not all independently reviewed and do not establish corpus precision or model token savings. The full loop-binding and model-efficiency goals remain incomplete.
